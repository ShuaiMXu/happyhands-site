## 哪些属于 Harness 工程问题

| 问题 | 直接归属 | Harness 应如何处理 |
| --- | --- | --- |
| 同一功能两套面板生命周期、全局 DOM 查询 | 官网实现 | 变更影响分析必须列出首页与资源页两个消费者；复核不能只看组件源文件。 |
| 间距、勾选图标、默认边界、嵌套折叠与背景叠加 | 官网样式与组件契约 | 要求展开、选中、键盘焦点及窄屏截图；静态扫描不能升级为视觉通过。 |
| 多窗口误报冲突、无修改仍保存 | 官网状态管理（P0） | 纳入双窗口无编辑同步、真实冲突、草稿保留的功能复核场景，不能仅凭截图判断正确。 |
| 多次反馈同类 UI 缺陷 | 复核流程覆盖不足的风险 | 把反馈转成任务相关的必检状态和消费者清单，记录实际证据；仅在 rubric 追加文字还不够。不能据此推断每个历史 run 都错误放行，需逐个查验。 |
| 发布包带研究数据、证据目录持续增长 | 网站构建边界 / Harness 生命周期治理 | 分别制定发布白名单与证据归档政策。属于 P2/P3，不通过直接删除证据解决。 |

### 已存在的能力，不应重复造轮子

已核查核心工程 `packages/workbench/ai-review.js`：

- 使用 stateId + configurationId 匹配前后截图；计划包含动作、到达状态与最终状态证据。
- 独立 QA 读取 visual-hierarchy-reviewer/rubric.json，并记录内容哈希。
- 复核提示明确要求：未检查截图、缺少正常交互证据或范围外状态不得推断通过，应返回 needs-evidence。
- 因此，现有证据不足以认定“核心执行器没有复核能力”。优先补的是具体项目的状态计划、消费者覆盖与验收记录，而不是再新增一个相同的评分器。

### 建议的工程补强顺序（尚未实施）

1. 任务范围 → 必检状态清单：下拉展开/选中/焦点、折叠展开、输入框默认/错误、工具往返切换、双窗口冲突；只加入本次相关项。
2. 共享组件 → 受影响消费者清单：每个入口必须有对应的状态证据或明确排除理由。
3. 验收记录校验：将清单与现有 plannedCaptures、verification.records 对照；不足项保持 needs-evidence。先审计实际 run，确认哪里没有执行已有约束，再改核心判定逻辑。
4. 证据生命周期：保留源版本、规则版本、原图、检查结果与人工结论；再做归档、索引和可恢复清理。
